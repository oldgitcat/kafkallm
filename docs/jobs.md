# Jobs and manual Kafka submission

[Back to the main README](../README.md)

## Kafka message envelope

A job is a single JSON document on the `jobs.in` topic. There is no wrapper
object and no separate metadata record.

| Part | Value |
|---|---|
| Topic | `jobs.in` (`JOBS_TOPIC`, default `jobs.in`) |
| Key | `job_id` as UTF-8 bytes. Recommended; the worker reads the ID from the JSON value. |
| Value | JSON object matching the `Job` schema |
| Headers | Optional W3C `traceparent` / `tracestate` bytes. If omitted, the worker starts a new trace. |
| Broker (host) | `127.0.0.1:19092` |
| Broker (Compose) | `kafka:9092` |
| Consumer group | `agent-workers` (workers only; a manual producer does not join it) |

The worker validates the value with `Job.model_validate`; unknown fields are
rejected. A manual producer can omit `job_id` and `run_id`, but then it cannot
use the generated `job_id` as the Kafka key. Set both explicitly.

`traceparent`/`tracestate` are optional. The CLI and GUI inject them so the
`job.submit` span and the worker trace are connected. A raw producer without
headers still works; the worker creates a new trace ID.

## Minimal message

This is enough for a default job:

```json
{
  "instruction": "Write /workspace/outputs/hello.md with one line: hello"
}
```

The worker fills in the defaults: `type=llm_task`, `sandbox=default`,
`multi_agent=true`, `agents=[]`, `input={}`, `input_files=[]`,
`unlimited=false`, `timeout_seconds=300`, and `reflect=null` (worker default).
The image comes from the `default` sandbox registry entry.

## Full example

```json
{
  "job_id": "0f3f7f3e-6f0b-4a9a-9b9a-1b2c3d4e5f60",
  "run_id": "c1e9a8b7-6d5c-4b3a-8f2e-1a0b9c8d7e6f",
  "type": "llm_task",
  "trace_id": null,
  "instruction": "Analyze /workspace/inputs/00-tool.bin and write a report.",
  "input": {"language": "en"},
  "input_files": [
    {"bucket": "jobs", "key": "uploads/example/tool.bin"}
  ],
  "sandbox": "reverse",
  "sandbox_image": "kafkallm-rea-job:latest",
  "multi_agent": true,
  "agents": [],
  "unlimited": false,
  "timeout_seconds": 900,
  "reflect": false
}
```

## Field notes and limits

- `type` must be `llm_task`.
- `instruction` is required, 1–100,000 characters.
- `job_id` / `run_id` must match the ID pattern (UUID-like safe strings).
- `input` is JSON and limited to 256,000 bytes. Put larger data in a file and attach
  it with `input_files`.
- `input_files` contains S3/RustFS references (`{"bucket": "...", "key": "..."}`).
  `kafkallm submit --upload FILE` uploads and fills this list for you.
- `sandbox` names a built-in (`default`, `reverse`) or a GUI registry entry.
  If `sandbox_image` is omitted, the worker uses the registry image. A manual
  job with an unknown `sandbox` must provide `sandbox_image`.
- `sandbox_image` is an OCI reference; the worker checks local Podman storage
  first and pulls the image if it is missing.
- `agents` must contain complete `AgentSpec` objects. The GUI's `agent_ids`
  shortcut is not accepted on the raw Kafka path.
- `timeout_seconds` is 1–3600. The worker also enforces
  `MAX_JOB_TIMEOUT_SECONDS`; Goose turn limits are controlled by
  `GOOSE_JOB_MAX_TURNS` / `GOOSE_JOB_SUBAGENT_MAX_TURNS`.
- `unlimited=true` is rejected unless `ALLOW_UNLIMITED_JOBS=true` on the worker.
- `reflect` is `null` (worker default), `true`, or `false`.

## Producing a job manually

### CLI (recommended)

```bash
kafkallm submit --job-json job.json
```

Or from stdin:

```bash
kafkallm submit --job-json - < job.json
```

The CLI validates, injects trace headers, adds the sandbox image, publishes to
`jobs.in`, writes the initial `queued` state, and prints the final job JSON.

### Raw Kafka producer

```python
import json
from confluent_kafka import Producer

job = {
    "job_id": "0f3f7f3e-6f0b-4a9a-9b9a-1b2c3d4e5f60",
    "instruction": "Write /workspace/outputs/hello.md with one line: hello",
}
producer = Producer({"bootstrap.servers": "127.0.0.1:19092"})
producer.produce(
    "jobs.in",
    key=job["job_id"].encode(),
    value=json.dumps(job).encode(),
    # Optional W3C trace context:
    # headers=[("traceparent", b"00-...-...-01")],
)
producer.flush(30)
```

`job_id` and `run_id` are generated by the model if omitted, but if you omit
`job_id` you cannot use it as the key. The worker reads the job from the value.

### Kafka UI

Open <http://localhost:8080>, go to **Topics → jobs.in → Produce Message**, set
the key to the `job_id`, and paste the JSON into the value. Kafka UI does not
expose custom headers in the simple form; the job still runs, but its trace
starts at the worker.

## Results, state, and events

| Topic | Payload | Use |
|---|---|---|
| `jobs.out` | `JobResult` | Final result and artifacts |
| `jobs.state` | `JobState` (compacted) | GUI database / latest state |
| `jobs.logs` | `JobLog` | Live activity |
| `agent.events` | Audit event | Submission, worker, Goose, artifacts |
| `jobs.cancel` | `JobCancel` | Stop request |

Read them with the CLI:

```bash
kafkallm results --from-beginning
kafkallm states --from-beginning
kafkallm events --from-beginning
kafkallm logs --from-beginning
```

The complete `Job` and `JobResult` schemas are available with
`kafkallm schema job` and in the GUI's `/api/schema/job` endpoint.
